# Personal Info Detection: Design

## Purpose

Scans files for content that looks like Dutch personal information:
full names, addresses, and email addresses. Used by the pre-commit
hook, pre-push hook, and the GitHub Action, all via the same shared
module (personal_info.py / personal_info.sh).

## Files skipped before scanning

- Binary files: detected by checking for a null byte in the first
  8192 bytes.
- Markdown files (.md): documentation frequently contains realistic
  example names/addresses. Skipping .md removes a large source of
  false positives with little loss of real coverage.

## Reference data

Three plain-text lists, one entry per line, in personal-info-lists/:
common-dutch-firstnames.txt, common-dutch-surnames.txt,
common-dutch-streetnames.txt. Generated by separate private repos
(dutch-name-reader, dutch-streetname-reader) and committed here, not
generated at build time.

## Matching approach: set membership, not regex alternation

The lists are large (10k-150k entries). A regex built by joining them
all with `|` would be slow to compile and slow to run on every line
of every file. A Python `set` gives O(1) lookup regardless of list
size.

First names are single tokens, loaded into one set. Surnames and
street names can be multi-word ("ter Hart", "van der Berg", "Van
Gogh straat"), so both are grouped by word count into separate sets
and matched via a sliding window over adjacent tokens, checking the
longest possible group first so a longer match isn't missed in favor
of a shorter overlapping one.

## Full name detection

A match requires a known first name adjacent to a known surname, in
either order ("Jan Smit" or "Smit Jan"). Both sides must be present
in the reference lists; matching is case-sensitive. This is
deliberately stricter than an earlier version, which accepted a known
name plus ANY capitalised word on the other side, a much weaker
signal that produced many more false positives.

A candidate match is discarded (not a violation) if the line also
contains any of:

- a Dutch street suffix (straat, laan, weg, etc.): avoids flagging
  street names like "Jan van Galenstraat" as a person's name
- an institution name (ziekenhuis, kliniek, hospital, clinic)
- a "post-" prefix
- documentation metadata keywords (author, copyright, maintainer,
  contributor, created by, written by, owner, unit owner, code owner)

## Address detection

Only known street names (from common-dutch-streetnames.txt) are
matched, via the same n-gram approach as surnames, followed by a
house number. There is no fallback pattern for streets outside the
list: the underlying BAG/PDOK data is close to exhaustive for the
Netherlands, so a generic "capitalised word ending in a street
suffix, followed by a number" fallback was judged to add
false-positive risk without covering a meaningful real gap.

A known street with no house number following is still flagged, as
the separate, lower-confidence category "Address (no number)".

## Email detection

Matches a standard email pattern, excluding common placeholder
local-parts (example, info, noreply, support, admin, etc.) and
placeholder domains (example.com, example.nl, etc.), so documentation
and boilerplate code don't trigger false positives.

## Detection order and early exit

Per line: email check first, then full name check, then address
check. As soon as one violation is found on a line, the remaining
checks for that line are skipped, so at most one violation is
reported per line.

## What was removed and why

- **Patient ID / BSN detection**: removed entirely. False-positive
  rate was too high, especially against medical ontology files
  (SNOMED, ICD) containing many numeric IDs of the relevant length.
  Elfproef checksum validation on BSN reduced but didn't eliminate
  the noise.
- **Unlisted-street fallback pattern**: see Address detection above.

## Shared module, not duplicated per entry point

personal_info.py / personal_info.sh contain all of the above. The
precommit and prepush entry scripts (in both languages), and the
GitHub Action's personal-info-check.py, only differ in how they
select which files to check and in their user-facing messages. This
is intentional: detection behaviour cannot drift between them because
there is only one implementation of it.

## Case sensitivity

Full-name matching is case-sensitive. This reduces false positives
from lowercase words that coincide with a name (e.g. a variable named
`max` no longer matches the first name "Max"), at the cost of missing
a genuine name typed in all-lowercase, judged an acceptable trade-off.
